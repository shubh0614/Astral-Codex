# Working Instructions for Claude Code

This is a personal, non-commercial research project. Read this file first, it tells you how to operate on this repo. Then follow the steps below before doing any actual work.

## Mandatory session start sequence

1. Read `continuity.md` in full. This is the current-state log: it tells you what phase we're in, what's done, and what's next. Trust it over your own assumptions.
2. Read `plan.md` Section 0 (revision history) and Section 7 ("Workflow Phases") to confirm which phase is active.
3. Do not jump ahead of the current phase. If `continuity.md` says we're in Phase 0 (Corpus Viability Sprint), do not start writing fine-tuning code, even if it seems like a natural next step: ask the user first.
4. **The plan is LOCKED at v3.2 (8 independent external LLM reviews across 4 rounds, all converged).** Do not propose further architecture revisions or re-litigate settled decisions (genre schema, vertical-slice ordering, guardrail mechanism, fine-tuning-as-conditional, the frozen research question in plan.md Section 1.5) unless real data from Phase 0 or later surfaces a concrete, specific problem. If the user brings a new external review, read it, extract anything genuinely new and evidence-based, but push back firmly on pure re-planning: the project has had more than enough of that and needs real data now, not another opinion.
5. If anything in `continuity.md` or `plan.md` seems outdated, contradicted by the current chat, or wrong: say so and ask, don't silently resolve it yourself.

## Mandatory session end sequence

Before ending a session (or whenever the user says to wrap up), update `continuity.md`:
- "Current Phase / Status"
- "Last Session Summary" (add a new dated entry at the top, terse: a few bullet points)
- "Next Immediate Steps"
- "Key Decisions Log" (append any new decisions, never edit old ones)
- "File Map" (add any new files created this session)

This is not optional. The project spans many sessions and this file is the only thing preventing context loss between them.

## Git conventions

- Commit at every meaningful checkpoint: directory setup, each tradition's fetch, each annotation pass, each phase gate passed. Don't batch a session's work into one giant commit at the end.
- Push to GitHub at each checkpoint, not just at session end.
- **Commit messages must read as human-written, not AI-generated.** Plain, specific, describe what actually changed. No boilerplate preamble, no generic "Update files" or "Implement feature X" filler.

## Writing style (applies to everything: docs, notes, comments, commits)

- **Never use em dashes or en dashes.** Not in prose, not in headings, not in comments, not in commit messages. Use a comma, a colon, a full stop or parentheses instead. This is absolute, there is no exception for "it reads better here".
- No decorative unicode in prose (arrows, emoji, bullets). Plain ASCII. Drawing characters inside fenced diagram blocks are fine.
- Avoid the usual LLM vocabulary: delve, crucial, robust, seamless, leverage, comprehensive, pivotal, testament to, it's worth noting, in conclusion.
- Comments explain why something non-obvious was done. Do not write comments that restate the code. Long rationale belongs in `notes/`, not in a docstring.
  - Good: `add Babylonian sample fetch, 94 candidates pulled`, `annotate Roman sample, 22/30 usable`, `fix katun conversion off-by-one for pre-1000 CE dates`
  - Bad: `Update Babylonian data files`, `Implement annotation pipeline`, anything that sounds like a changelog entry rather than something a person typed while working.
- **Never include `Co-Authored-By: Claude`, `Generated with Claude Code`, or any similar attribution trailer in a commit.** This applies to every commit, not just ones from an explicit instruction: treat it as a standing rule, not a one-off request.

## Working principles for this project

- **Facts vs. style is sacred.** Any concrete astronomical claim (which planet, which constellation, what conjunction) must come from the deterministic astronomy engine, never be freely generated by the language model. If you're ever building something that lets the model invent astronomical facts, stop and flag it.
- **Data fetch phase = store raw, unmodified text first.** Don't clean-and-discard in one step. Keep `data/raw/<tradition>/` as an unmodified snapshot of whatever was fetched, separate from `data/processed/`.
- **Copyright is not a blocker for this project** (personal, non-commercial, no redistribution). Don't add copyright-compliance friction to fetch scripts. This may change if the user says they're planning public release: if that happens, flag it and revisit source-by-source.
- **Excluded sources stay excluded.** Aboriginal Australian material is excluded on ethical (not legal) grounds: do not suggest re-including it, do not search for workarounds. This is a firm boundary, not a search-harder problem.
- **Small corpora, real risk of overfitting.** When we get to fine-tuning, watch validation loss closely, keep LoRA rank modest, don't be surprised if results need multiple iterations.
- **This is exploratory research, not production software.** Prioritize getting something working and inspectable over premature engineering (no need for elaborate abstractions, config systems, or test suites unless the user asks).
